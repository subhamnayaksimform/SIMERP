SECTION 4 Rule-wise Analysis (Violated Rules Only)
SEC-BE-02 Insecure HTTP / protocol usage Critical

What was found: The optional VITE_WS_BASE_URL is normalized with the standard URL parser but is not restricted to HTTPS, then the resulting origin is used for a Socket.IO connection configured to send both an authentication token and browser credentials.

Files affected: src/lib/env.ts:23 — accepts any URL protocol; src/lib/env.ts:43 — exports the unchecked WebSocket origin; src/services/notifications/notificationsSocket.ts:31 — opens the credentialed connection.

const toOrigin = (url?: string): string | undefined => { const trimmed = url?.trim(); if (!trimmed) return undefined; try { const { origin } = new URL(trimmed); return origin; } catch { return undefined; } }; export const WS_BASE_URL = toOrigin(env.VITE_WS_BASE_URL) ?? toOrigin(env.VITE_API_BASE_URL); return io(resolveNamespaceUrl(), { auth, withCredentials: true, autoConnect: false, });

Why this violates the rule: A remote value such as http://notifications.example.com passes normalization, allowing authentication material to cross an unencrypted transport despite the API proxy's separate HTTPS check.

Remediation steps:

  1. Validate VITE_WS_BASE_URL and VITE_API_BASE_URL origins so non-loopback targets must use HTTPS.
  2. Fail the build or application startup with a clear configuration error when a remote plaintext origin is supplied.
  3. Add tests covering rejected remote HTTP origins and allowed localhost development origins.
