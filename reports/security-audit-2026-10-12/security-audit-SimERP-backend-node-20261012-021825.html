SECTION 4 Rule-wise Analysis (Violated Rules Only)
SEC-BE-05 Hardcoded secrets in source/config files Critical

What was found: Swagger Basic Auth falls back to the literal password admin123 when SWAGGER_PASSWORD is absent; Swagger is enabled in local and development environments.

Files affected: src/config/app.config.ts:28 — hardcoded default Swagger password.

swaggerUsername: process.env.SWAGGER_USERNAME || 'admin', swaggerPassword: process.env.SWAGGER_PASSWORD || 'admin123',

Why this violates the rule: A committed default credential is predictable and can become an active authentication secret through configuration omission.

Remediation steps:

  1. Remove the literal username and password fallbacks from application configuration.
  2. Require and validate SWAGGER_USERNAME and SWAGGER_PASSWORD whenever Swagger is enabled.
  3. Fail startup rather than enabling documentation with missing or placeholder credentials.
SEC-BE-06 Sensitive data in logs or error responses High

What was found: Employee sync paths interpolate employee names, email addresses, internal numeric IDs, and failure text directly into the logger message string; the logger redacts metadata keys but does not sanitize message text.

Files affected: src/modules/zoho-analytics/employees-metadata.service.ts:910 — name and email in warning; src/modules/zoho-analytics/employees-metadata.service.ts:970 — name and email in warning; src/modules/zoho-analytics/employees-metadata.service.ts:1015 — name, email, and internal ID in success log; src/modules/zoho-analytics/employees-metadata.service.ts:1018 — name, email, and raw failure text in error log.

this.logger.warn( `[EmployeesMetadataService] New employee pre-check — ${row.name} (${row.email}) excluded before create: department '${row.department}' not found`, ); for (const [i, result] of results.entries()) { const row = newRows[i]; if (result.status === 'fulfilled') { this.logger.log(` ✓ ${row.name} (${row.email}) — id: ${result.value.id.toString()}`); } else { this.logger.error( ` ✗ ${row.name} (${row.email}) — FAILED: ${result.reason instanceof Error ? result.reason.message : String(result.reason)}`, ); } }

Why this violates the rule: Names and email addresses are personal data, internal IDs reveal implementation details, and raw exception messages may carry sensitive upstream content; interpolation into message bypasses the key-based SENSITIVE_KEYS redaction applied only to metadata.

Remediation steps:

  1. Use constant log messages and move permitted context into structured metadata.
  2. Identify employees only by public UUID and never log names, email addresses, or internal BigInt IDs.
  3. Map failures to stable error codes instead of logging raw exception messages.
  4. Add tests proving sensitive values cannot appear in either log messages or metadata.
